headless-bookkeeping · планы 02–06

Переосмысление отображения данных: каждый экран

Не «новая тема поверх таблиц», а другой способ показывать данные. Сначала — восемь глобальных правил, потом каждый экран: что не так сейчас (из аудита кода) и как будет.

1 · ID — не данные

ID · Category · Gross → Контрагент · сумма · статус. Сырой ID уходит в URL и деталь. Первая колонка всегда отвечает «что это?», а не «какой номер строки в базе».

2 · У каждого объекта есть деталь

Сейчас у Expense/Invoice/Approval вообще нет detail-экрана — только строка таблицы. Каждый объект получает свой роут: hero-сумма, факты, провенанс, связи. Ни одного тупика.

3 · Причина — человеческим языком

policy_reason: amount_over_ceiling → «89,00 € выше лимита 50,00 €». Показываем порог и факт, а не код. Оператор принимает решение, не расшифровывает.

4 · Прогрессивное раскрытие

Список отвечает на «что требует решения», деталь — на «какие факты», раскрытие — на «откуда факты» (OCR markdown, классификация). Не тащить всё в таблицу.

5 · Суммы и даты — по стандарту

Деньги: tabular-nums, справа, входящие зелёным с «+». VAT из списков уходит в деталь. Даты: относительные в списках («2 ч назад»), абсолютные в деталях.

6 · Секции с итогами вместо пагинации

Списки группируются по времени (месяц/сегодня-вчера) с итогом в заголовке секции. Итог месяца — данные, которые сейчас вообще нигде не видны.

7 · Формы: prefill → подтверждение

Всё, что система знает (OCR, память поставщика, ставка VAT страны, последняя категория) — уже заполнено. Оператор сверяет и правит, а не вводит с нуля. Суммы только в евро.

8 · Выбор объекта — не ввод ID

«Object ID: ___» (Credit notes сейчас) → поиск по списку с контекстом (номер, контрагент, сумма, остаток). Руками ID не вводят никогда.

Старые сверху — очередь разбирается FIFO

Строка = решение: кто · почему · сколько · когда

Решения

  • Заголовок строки — контрагент, не filename и не «Expense #214». Filename только если контрагента ещё нет, и тогда подзаголовок — вопрос («кто это?»).
  • Подзаголовок — причина с числами: «89,00 € выше лимита 50,00 €», «уверенность 0.41 — проверь категорию». Порог и факт из policy-конфига, не код.
  • Сортировка FIFO (старые сверху) с секциями «Сегодня / Вчера и раньше» — очередь должна кончаться, застрявшее — на виду.
  • Confidence показываем только низкую — высокая не мусорит список.
  • Desktop: те же строки + hover-кнопки Approve/Reject прямо в строке; хоткеи j/k/e/r. Мобайл: свайпы + деталь.
  • Живое обновление: polling — OCR-статусы меняются сами, без передёргивания руками.

Сумма — герой, причина — объяснение, документ — рядом

Решения

  • Иерархия: сумма → причина → документ → факты. Решение принимается за 3 секунды, если всё сходится.
  • «Почему держим» — жёлтый блок с конкретикой из policy-конфига. Единственное, что реально надо прочитать.
  • Превью документа — тап в fullscreen. Оператор сверяет сумму с бумагой, не верит на слово.
  • Reject — bottom sheet с полем причины (обязательным): причина уходит в draft, объект не удаляется (ADR-0015).
  • Режим разбора: «1 из 3» + автопереход к следующему pending после действия. Очередь щёлкается подряд.
  • Работает для всех object_type (expense, invoice, dividend, personal, correction) — шаблон один, факты свои.

Поставщик — заголовок; месяц — секция с итогом

Решения

  • Invoices — зеркально (номер + customer вместо поставщика, Sent-статус чипом).

Строка без счёта — главный сценарий, не edge case

Сейчас — главная боль всего продукта: открываешь выписку, а матчить не с чем — счетов в системе нет. Чеки живут в iOS-приложениях банка и вендоров. Ради каждой строки — экспедиция: найти чек в чужом приложении, выгрузить PDF, залить, дождаться OCR, оттриажить, вернуться в выписку, сматчить. Переворачиваем флоу: расход создаётся из самой строки, документ догоняет потом.

Один тап: строка выписки → проведённый расход

Решения

  • Один тап от строки до закрытой позиции. В строке выписки уже есть всё для расхода: сумма, дата, контрагент. Расход создаётся из неё и матчится автоматом — оба вызова (POST /api/expenses + POST /match) в API уже существуют, флоу собирается на клиенте.
  • Prefill из трёх источников: контрагент по алиасам (WOLT → Wolt Eesti OÜ, ADR-0014), категория из classification memory («обычно Meals, 8 из 9»), VAT авто по ставке страны, дата из строки. Незнакомый контрагент → мини-шаг «создать поставщика» прямо в этом же sheet.
  • «Ждут документ» — очередь вместо экспедиции. Расход без source-документа получает маркер и попадает в очередь в Books. Чек, приплывший позже через intake (переслал письмо, сфоткал, e-mail-коннектор сам вытащил) — автоматически предлагается приклеиться по совпадению «поставщик + сумма ± дата». Охота по iOS-приложениям превращается в «когда-нибудь перешлёшь — само найдёт куда».
  • «Чека не будет» — круассан-кейс. Мелкая трата, документа не существует и не появится. Проводим сразу: первичкой служит сама строка выписки, VAT автоматически 0 (без счёта входной VAT не вычитается — форма знает это правило за оператора), в очередь «Ждут документ» не попадает, наги не приходят. В детали расхода источник так и подписан: «строка выписки SEB · 27.06». Guardrail через Policy: no-doc расходы выше настраиваемого порога (например 50 €) уходят на approve — круассан проскочит, «без чека на 500 €» спросит подтверждение.
  • Повторяющиеся траты — «как в прошлом месяце»: Telia/AWS/аренда каждый месяц. Если у контрагента есть расход в прошлом периоде — предложение в один тап: категория и VAT из прошлого, сумма из строки.
  • Bulk: выделил 6 однотипных строк → «создать 6 расходов» разом, каждая по своему prefill.
  • Честно про API: create+match работают уже сейчас; alias-lookup по строке выписки и авто-приклейка позднего документа к существующему расходу — небольшие серверные добавки, помечаю их как требования плана 04 (это осознанное расширение client-only скоупа — оно того стоит, это ядро боли).

Объяснение + баланс долга, не бухгалтерия

Решения

  • Никакого выбора счёта. Проводку резолвит country plugin по org_type — оператор видит только последствия человеческим языком: «не попадёт в P&L, VAT не вычитается, повиснет долгом».

  • Approve-on-the-spot: personal требует approval (ADR-0017), но оператор и есть approver — один атрибутируемый тап записывает и disposition, и approval в аудит. Без пинг-понга через Inbox.

  • Если у плагина есть advisory для юрисдикции (например, датский kapitalejerlån «верни немедленно») — показывается в этом же sheet жёлтым.

Каждая строка декларации раскрывается до расходов

Решения

  • Drill-down: каждая строка KMD раскрывается в составляющие объекты, каждый кликабелен → деталь. Цифра трассируется до расхода в два тапа — киллер-фича доверия к отчёту.
  • Явная маркировка live-превью vs frozen snapshot (open/locked период) — сейчас неразличимо.
  • INF-предупреждение ведёт прямо к полю конкретного расхода (metadata-PATCH, пока период open), не «где-то что-то не так».
  • «Не решено в периоде» — виден straggler-хвост до закрытия, ссылкой в Inbox с фильтром.
  • Lock — sheet-flow: список нерешённого + «поздние документы уйдут в следующий период» + подтверждение (ADR-0015 warn-and-confirm).
  • Периоды-список: статус open/locked + fold submission-событий (accepted ✓ / rejected / not filed) + timeline подачи с «Add event» (ADR-0037).

Используется какподсказка AI, не правило

Идентичность + связи + память в одной карточке

Решения

  • Деталь-роут вместо inline-edit в таблице: reg key (иммутабельный — видно почему), связанные расходы/документы счётчиками-ссылками с суммой.
  • Алиасы — чипы в карточке, не отдельная панель внизу страницы. Добавление на месте.
  • Память классификации видима: «обычно Fuel (11 из 12) · подсказка AI, не правило» — оператор понимает, почему AI предлагает то, что предлагает (ADR-0014 advisory).
  • Список: имя + role-чип (supplier/customer/claimant) + страна, поиск. ID — нет.
  • Claimant-роли видны отдельным фильтром (для reimbursement-флоу, ADR-0036).

Остальные экраны — решения без макетов

Documents — архив

Крупный thumb + заголовок = поставщик (filename — только пока не распознан) + канал-иконка + relative time + статус-чип. Фильтры-чипы: Все / Processed / Needs triage / Discarded (ADR-0038) / Errors. Деталь строго из персистнутых intake-артефактов (ADR-0039): классификация KeyValue, OCR-markdown в collapsible, ссылка на созданный expense. Upload-sheet: файл + опциональный claimant-dropdown (ADR-0036).

Credit notes

Создание — из детали инвойса/расхода (кнопка «Issue credit note»), объект уже известен. Отдельная форма остаётся, но «Object ID: ___» → выбор из списка с поиском (номер · контрагент · сумма · остаток). Суммы в евро (фикс cent-бага). Список — как Books-сегмент со ссылками на объект.

Bank import — flow

Отдельный экран со степпером: Upload → LLM выводит mapping → Rules применяются → Statement создан. Каждый шаг со статусом, ошибка схемы = явный failure-экран с «загрузить заново» (ADR-0031: свежий inference каждый раз, «дрейф формата — не событие»).

Settings — все формы

Grouped-list хаб (iOS Settings). Org: country/currency — селекты ISO, не free-text. Policy/Risk gate: центы → евро, thresholds с объяснением эффекта («расходы выше X идут на approve»). Mailbox: коннекторы со статусом sync + last error видимым. Enroll: QR + понятная ошибка при неконфигурированном public_api_url. Categories: read-only справочник с пояснением «владеет country plugin».

Что это меняет в планах 02–06

Каждый план получает не «перекрасить экран», а конкретные data-display-спеки из этого документа: план 02 — Inbox (§1–3), план 03 — Books (§4–5 + Documents + Credit notes + очередь «Ждут документ»), план 04 — Bank (§6★ «расход из строки» — центральный сценарий всего редизайна + §6 + import; включает два небольших серверных дополнения: alias-lookup по строке и авто-приклейку позднего документа), план 05 — Reports (§7), план 06 — Settings + Entities (§8–9). После твоего одобрения вношу это в spec как каноничное описание экранов.
