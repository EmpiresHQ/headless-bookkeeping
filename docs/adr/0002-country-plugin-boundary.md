# Country-plugin boundary: thin canonical kernel, country specifics in plugins

The kernel owns a thin canonical chart of Accounts — Cash, Bank (per currency), AR, AP, Revenue, Expense-by-category, VAT-payable, VAT-receivable, Equity, Customer-prepayments, Supplier-prepayments/prepaid-expense, FX-gain/loss, Bad-debt-expense, Accumulated-depreciation + Depreciation-expense (when assets are enabled), and Suspense. These are universal double-entry mechanics, country-agnostic. A country plugin owns everything country-specific: the authoritative VAT codes (e.g. `DK_INPUT_25`), VAT rates, deductibility rules, `category → account + vat_code` mappings, rounding, and report export formats. A plugin may extend/refine the chart, never replace it.

Two deliberate decisions:

- **VAT reports are built from the country-specific VAT code.** There is no abstract, kernel-canonical VAT vocabulary. We considered a thin canonical "VAT treatment" layer (`REVERSE_CHARGE_SERVICES`, …) to feed AI and make supplier memory portable across countries, and rejected it: deciding a code's applicability requires country context regardless, so the abstract layer earns the AI nothing, and the only remaining use (cross-country analytics) is not a real need for single-country freelancers / micro-SMBs. It can be re-added later as derived data if multi-country aggregation becomes a requirement.
- **The country plugin is the sole resolver of a VAT code**, from `(Supplier intrinsic facts + the Organization's country/registration)`. A Supplier stores only intrinsic, context-free facts (country, goods-vs-services, default category, aliases) — never a VAT code, because the code depends on the Organization's context.
- **Cross-border VAT treatment is a plugin decision, keyed on VAT-territory membership — not the political country.** The plugin maps a Supplier's country to a *VAT territory* (EU VAT territory / EAEU / third country — note the EU VAT territory excludes e.g. the Canary Islands and includes e.g. Monaco) and decides, from `(our territory + supplier territory + goods-vs-services + whether VAT was charged)`, whether a purchase is domestic, reverse-charged, an import, or a non-reclaimable foreign cost. Reverse-charge uses *our* VAT code; we do **not** need to know foreign VAT codes. Both the territory-membership map **and** the eligibility rule live in the plugin (each plugin encodes its own jurisdiction's view; the EU list duplicated across EU plugins is acceptable because the rules-perspective differs per country). This does **not** reintroduce the rejected canonical VAT layer (§ above): a territory-membership map is neutral geography/treaty reference data, not a VAT-code vocabulary. The kernel **never silently reclaims a foreign `document_vat_marking`** as input VAT; an unresolvable treatment is held for Approval (ADR-0015), conservative default being gross-as-cost. The real carrier of this is the Supplier's `country` (captured once at supplier onboarding, ADR-0014) — OCR only supplies corroborating evidence, never the decision.

The plugin boundary also owns the jurisdiction's **default base currency** (`getDefaultBaseCurrency()`) and **reporting period frequency**, alongside VAT. The Organization may override the base currency (see ADR-0004); absent an override it inherits the plugin's default.

Chosen over a fully kernel-canonical model (too rigid for divergent national VAT regimes) and a fully plugin-defined model (duplicates ledger/reporting logic per country).

## Wave-6 amendment — observable plugin resolution + a real (two-adapter) seam

Two seam-hardening decisions, closing friction #6 and the ADR-0005 wave-gate gap:

- **`PluginLoader.resolve()` fallback is observable, not silent — warn, not throw.** When no dedicated plugin is registered for a country code, resolution falls back to the neutral `NullCountryPlugin` (Ireland/EUR defaults). Previously this returned silently, so a DK org would book against IE-ish defaults with no signal. It now emits a NestJS `Logger.warn`. **Warn, not throw**, because the default deployment legitimately runs on the neutral plugin (ADR-0004) — a throw would break it and every existing test; a warning surfaces the misconfiguration without breaking a valid neutral-plugin deployment. **Spam control:** the warning fires once per distinct unknown country code (a `Set` of already-warned codes), not once per `resolve()` — `resolve()` runs per voucher, so a busy unconfigured deployment gets one warning, not one per posting.

- **A second adapter makes the seam real.** "One adapter = a hypothetical seam." `NullCountryPlugin` is deliberately permissive (every VAT code it emits is valid), so a semantic Rule can never fail through it and the Override path (ADR-0005) is unreachable with it as the sole plugin. `StrictTestPlugin` (`src/plugins/strict-test.plugin.ts`) is the strict counterpart: it extends `NullCountryPlugin` and FORCES a semantic failure for one known-bad input (the Category `strict-test-category` maps to VAT code `STRICT_REJECTED`, which its `validateVATCode` then rejects). It is **TEST/DEV ONLY** — wired only by overriding the provider in the override-pipeline e2e — and never enters the production default deployment, which stays on `NullCountryPlugin`. This is what makes the ADR-0005 override-path test (semantic failure → Approval → logged Override → post, with the `override` row asserted) exercisable.

- **The kernel owns the non-VAT-reportable sentinel `NULL_VAT_CODE` (`'NULL_STANDARD'`), and that is *not* a breach of "no kernel-canonical VAT vocabulary" above.** The sentinel is a *posting marker* tagged on lines that carry no VAT at all (AR, AP, Bank, Equity); the posting layer and VAT report filter these out **before** any plugin VAT resolution runs, so the sentinel is never resolved *as* a jurisdiction VAT code. It is a double-entry mechanic (like the canonical Account chart), not a VAT-code vocabulary — so it correctly lives in the kernel (`src/ledger/posting/vat-constants.ts`) rather than being imported *from* a country plugin (its previous, inverted locality). A plugin still owns every real jurisdiction VAT code and may *reference* the sentinel among the codes it recognizes; it does not own it. This keeps "the plugin is the sole resolver of a (jurisdiction) VAT code" intact.
