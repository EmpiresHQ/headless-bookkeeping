# Prepayments / on-account balances; payment can be a VAT tax point

A payment can arrive before any invoice exists (retainers, deposits, "50% upfront" — common for freelancers/agencies). The reconciliation model previously assumed a payment always settles an existing AR/AP; prepayments break that assumption.

Decisions:

- **A prepayment is a liability, not a Receivable.** Money received before delivery means we owe delivery (or a refund), so it lands in a "Customer prepayments / payments on account" liability balance — never as AR. Symmetric on the buy side: paying a supplier in advance is a prepaid-expense / supplier on-account asset.
- **An unmatched incoming payment is an on-account balance, not an error.** It lands as a prepayment for that counterparty and is drawn down by one or more later invoices through the same N:M matching, with a two-sided outstanding (invoice: amount unpaid; prepayment: credit not yet consumed).
- **The kernel must not assume VAT arises only at invoice.** Under EU VAT Directive Art. 65, receiving an advance is itself a VAT tax point — output VAT can be due on receipt, before any invoice. The VAT engine takes the tax point from the country plugin; the advance-VAT computation and how it nets against later invoices (so VAT isn't double-counted) is a country-plugin rule.

Structure (liability + draw-down via matching) is built in v1; advance-VAT is implemented in the DK plugin first.

## Addendum (issue #201): an advance has an owner, a draw-down is an allocation

The structure above says a prepayment is drawn down "by one or more later invoices", but it never said where that link is recorded. Without one, a draw-down's effect had to be re-derived by summing every draw-down-shaped Voucher in the ledger — a ledger-wide figure that made unrelated advances move together, and candidate lookup had to inject the asking caller's counterparty into every prepayment Voucher it returned.

- **An advance belongs to one counterparty, decided at creation.** Ownership is established from evidence that belongs to the money — the caller's explicit counterparty, or the bank line's own confirmed IBAN / merchant-descriptor identifier — and persisted with the advance alongside the bank transaction it came from. Ambiguous or absent evidence yields an **unresolved** advance: visible, reported, and refused for allocation. Ownership is never inferred at query time from whoever is asking.
- **A draw-down is a persisted allocation**: source advance → target invoice, for that counterparty, for a base amount, evidenced by the posted clearing Voucher. An advance's remaining balance is its own amount minus its OWN active allocations (and active matches); nothing another advance does can move it. Cross-counterparty allocation is refused on both sides.
- **The allocation and its Voucher are written in one transaction**, after both remaining balances are re-checked on that connection, so concurrent or repeated draw-downs cannot overdraw an advance or over-relieve an invoice. Allocations are netted inside the canonical outstanding primitive, so a cash settlement cannot re-settle what a prepayment already relieved — and admissibility (registered, owned, verified, not reversed, counterparty-compatible) is enforced at every write path, not merely by hiding unsafe advances from candidate discovery.
- **A reversal releases exactly one allocation.** "Released" is derived from the ledger (`voucher.reverses_id`), never mirrored into a status column, so a reversal posted through any path frees that allocation's credit and no other. A reversed advance Voucher is cancelled credit: it never becomes available again.
- **Historical data is not guessed at.** Pre-existing advances are registered ownerless; pre-existing draw-downs are re-linked only where the ledger itself confirms the machine-written marker's whole shape. Anything unconfirmed leaves that kind's balances flagged **unverified** — reported as unknown and blocked, never as fully available. The operator repair path (`POST /api/prepayments/:voucherId/ownership`) assigns the owner and attributes the still-unlinked draw-down VOUCHERS to their source advance and target invoice; every link is verified against the ledger and capped by both sides' remaining balances. The flag lifts only when no unlinked draw-down of that kind is left. No posted Voucher is ever edited (ADR-0009).
