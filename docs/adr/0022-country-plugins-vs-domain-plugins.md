# Two plugin types: in-process country plugins vs out-of-process domain plugins

The kernel is extended along **two distinct axes**, and conflating them would either bloat the thin kernel or fragment the ledger.

- **Country plugin** (ADR-0002) — an **in-process, stateless rule resolver**. It owns country-specific *rules*: VAT codes, `category → account + vat_code` mapping, cross-border / VAT-territory treatment, reporting-period frequency, reference FX rate, base currency, org-type-dependent account choices. It has **no database of its own** — pure functions over `(Supplier intrinsic facts + Organization context)`. Exactly one is active per deployment (the Organization's country).

- **Domain plugin** (new) — an **out-of-process bounded context with its own database**, integrating with the kernel over an **API**. It owns a whole functional sub-domain end-to-end. The first is **payroll**: employees, gross→net breakdown, payroll-internal reconciliation, filing artifacts — all of that lives in the domain plugin's own store. The kernel ledger holds only a `SALARIES` (wage-expense) account plus payables and receives only the **summarized** result.

**The load-bearing invariant — a domain plugin never writes the ledger directly.** Despite owning its own DB, it is just another **source of draft Vouchers**, exactly like intake: it submits a summarized voucher (`Dr SALARIES / Cr net-pay-payable / Cr tax-payable / Cr pension-payable`) **through the kernel pipeline** (Rules → Policy → post), which is the only write path (ADR-0012 *no break-glass*, ADR-0019 *single write path*, ADR-0018 *everything funnels through the pipeline*). Its own database is an **operational** store (like the Conversation record or Mastra working memory), **not** the accounting system of record — the kernel SQLite ledger remains the sole SoR and the hash-chained truth.

**The cut (payroll example).** Kernel: the `SALARIES` expense account, the payables, and the one summarized payroll Voucher per run. Domain plugin: per-employee detail, gross→net computation, payslips, payroll-internal reconciliation. The **net-pay bank line is reconciled kernel-side** (against the posted net-pay-payable, via Wave-5 matching); **payroll-internal reconciliation** (which employee, which payslip) is the plugin's. The kernel never sees per-employee rows — only the aggregate posting crosses the API.

Chosen over (a) building payroll into the thin kernel (it is a domain on the scale of VAT/intake — wrong place, wrong lifecycle, country-specific in its own right) and (b) letting a satellite service write the ledger directly (would shatter the single-write-path / hash-chain integrity, ADR-0012/0019). Country specifics of payroll (IE PAYE/PRSI, DK A-skat) may themselves be resolved by a country plugin *inside* the payroll domain plugin — the two axes compose.
