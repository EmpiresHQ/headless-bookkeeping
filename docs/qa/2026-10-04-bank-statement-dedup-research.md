# Bank statement deduplication: research for issue 399

Date: 2026-10-04. Status: evidence and design questions, not an accepted design.

## Scope and evidence quality

[Issue 399](https://github.com/EmpiresHQ/headless-bookkeeping/issues/399) requires a canonical account transaction journal, overlapping source statements, preserved provenance, concurrent import idempotency, and previewable audited repair. The issue reports eight duplicate pairs totalling EUR 1,726.59, existing matches 17/18/23, fifteen unique statement9 operations, and a genuine separate EUR 14.05 transaction 137. Those are issue-reported production observations; this research did not access the production database or the local evidence directory named in the issue. No ledger-posting duplication is established by these observations.

Repository inspection below establishes implementation behavior. External claims use LHV's own documentation. No application code or production data was changed and no runtime tests were run. No AGENTS.md was found in the worktree or inspected ancestor directories. Existing dated investigation notes live under docs/qa, so this note follows that convention.

## LHV identity: what the provider actually documents

LHV's [internet-bank format specification](https://www.lhv.ee/en/formats-for-internet-bank), CSV format effective 25 February 2026, distinguishes payment reference (column 8), archival ID (9), entry reference (15), and account service provider's reference (16). Only the last of these is explicitly described there as the bank-assigned unique payment ID. The archival field's description gives a date-like format, not an explicit uniqueness guarantee. The same document allows configurable field and decimal separators; current `applyRules` configures neither a custom CSV delimiter nor a delimiter inferred by the mapping schema. These facts require checking the actual export headers/version, not guessing which issue-reported “transaction ID” means column 16.

LHV's [Connect account-statement documentation](https://docs.lhv.com/home/connect/services/account-reports/account-statement) identifies `AcctSvcrRef` as the bank's unique payment ID, emits booked entries, separates booking and value dates, and documents a reversal indicator. This supports separating identity, temporal facts and reversal semantics. It does not establish universal cross-provider identity rules or prove pending/booked identifier continuity for other feeds.

**Not established:** archival ID uniqueness; entry reference uniqueness in every CSV version; worldwide/account/currency scope of all historical LHV IDs; equivalence of the production issue's CSV ID column and documented column 16; pending-to-booked rules. Preserve all original identifiers and validate the actual exports before repairing history.

## Reconciliation and UI coupling

Reconciliation reads statement-owned rows and calculates remaining base-currency amount per transaction ID by summing active matches ([service, line 345](../../packages/server/src/reconciliation/reconciliation.service.ts#L345)). Thus two imported copies can independently appear open. Unique `(bank_transaction_id, voucher_id)` protects only the same stored pair, not two different transaction IDs representing the same real payment ([migration 031](../../packages/server/src/database/migrations/031_unique_reconciliation_match_pair.ts#L5)). Import also auto-stages proposals after marking the job done ([ingestion service, line 59](../../packages/server/src/bank/bank-ingestion.service.ts#L59)); dedup/conflict filtering must precede that stage.

Changing only repository list methods is insufficient. Candidate lookup explicitly checks `txn.statement_id === statementId` ([service, line 260](../../packages/server/src/reconciliation/reconciliation.service.ts#L260)). Bank account lookup joins through the owning statement in [settlement](../../packages/server/src/reconciliation/settlement-voucher.service.ts#L116), [FX](../../packages/server/src/reconciliation/fx-realized.service.ts#L490), [prepayment](../../packages/server/src/reconciliation/prepayment.service.ts#L223), and [personal disposition](../../packages/server/src/reconciliation/personal-disposition.service.ts#L93). Canonical account ownership and source membership must be separate concepts at these seams.

Repair must consider references beyond reconciliation matches: [advance allocations](../../packages/server/src/database/migrations/069_create_prepayment_advance_allocation.ts#L90) and [prepayment refund consumption](../../packages/server/src/database/migrations/079_add_prepayment_tax_treatment.ts#L140) reference bank transactions. These join the disposition/status and settlement checks required by the issue; an empty active-match list alone is insufficient evidence that a duplicate is financially unused.

The statement screen loads transactions, reconciliation, matches and proposals using statement-scoped keys ([screen](../../packages/web/src/bank/StatementScreen.tsx#L310), [queries](../../packages/web/src/queries/bank.ts#L33)), and builds lines by transaction ID ([model](../../packages/web/src/bank/statementModel.ts#L23)). Mutation invalidation currently refreshes only one statement's bank keys ([queries, line 166](../../packages/web/src/queries/bank.ts#L166)). Shared canonical state therefore needs all associated statement caches invalidated or canonical transaction keys. Counts/pagination must deduplicate before counting/slicing; source appearances may legitimately occur in multiple statement views, but account journal totals must not sum these appearances.

## Design decision tree for the interview

These are design questions, not implementation findings. During the interview the owner resolved two branches: no automatic merge without an authoritative ID (candidate review only), and quarantine conflicting rows while continuing unaffected imports. Remaining questions below stay open; the current decision record is in [DOMAIN-MODEL](../DOMAIN-MODEL.md).

1. **Identity scope.** Define the real bank-account identity separately from ledger account code. Is each BANK_* account guaranteed to represent exactly one provider/account/currency, or can multiple bank accounts map to one ledger account? Use provider + stable account identity + typed external ID; treat currency as a checked financial fact unless the provider explicitly scopes identity by currency. Adding currency to a uniqueness key without care could turn a same-ID currency conflict into two transactions.
2. **Strong IDs.** If an authoritative typed ID exists, insert/find atomically under a unique storage constraint. If two supplied authoritative aliases point to different canonicals, quarantine rather than choose the first. Same identity with incompatible amount/currency must preserve existing financial facts and produce review evidence.
3. **Missing IDs — owner decision: candidate review only, no automatic merge.** A full normalized-row fingerprint can find candidates but cannot distinguish two genuinely identical purchases. Prefer unresolved candidates/manual resolution for overlap ambiguity. Exact source replay can use source-artifact identity plus row occurrence, preserving multiplicity; reordered or partial overlapping files without strong IDs remain a separate ambiguity problem. Decide whether unresolved rows are excluded from the actionable journal until reviewed.
4. **Conflict transaction boundary — owner decision: quarantine conflicting rows, continue unaffected imports.** Partial progress needs durable row outcomes and retry behavior. Preserve source evidence and produce new/known/conflict counts without overwriting canonical facts. The remaining design question is how row review and retry reconcile with import completion states.
5. **Mapping versus identity policy.** ADR 0031 rejects hardcoded per-bank parsers and cached mappings. A deterministic provider identity policy can coexist with LLM column mapping, but only if its trust boundary is explicit: the model may suggest a column; it must not establish that a field is authoritative. Decide whether persisting mapping/version/source evidence is an intentional revision to the ADR's no-mapping-storage choice.
6. **Canonical/provenance model.** Candidate structure: account-owned canonical transaction; typed identity aliases; immutable import source/rows; source-row-to-canonical resolution; persistent conflict/review outcome. A statement-level many-to-many junction alone cannot retain duplicate occurrences and unresolved rows unless those concepts exist elsewhere.
7. **Detachment and repair.** Removing an association must not remove shared or financially referenced canonical records. Decide behavior when the last source is detached. For legacy repair, preserve matched IDs where possible, retain old-ID aliases, audit proof and preview impact, reject stale previews inside apply transaction, and guard all financial references. Keep financial reversal outside metadata-only merge.

## Verification needed before implementation is considered complete

- Recover the exact original exports and original mapping evidence if available. Confirm the eight identity pairs and negative control 137 from raw source; do not infer old IDs from generic null references.
- Add meaningful integration cases for both import orders, within-file repeats, renamed/reordered files, simultaneous imports, conflicting financial facts and preserved same-amount payments. Exercise both direct structured create and CSV ingestion, because both write transactions.
- Test repair preview/apply/retry/stale-preview with matches, drafts, dispositions and prepayment references; verify ledger postings remain unchanged for the eight metadata-only merges and statement9's unique operations remain.
- Test shared transaction state in both statement views, account totals/counts/pagination, source detachment, and cache refresh across associated statements.

The reproduced issue can guide fixtures, but its numeric record IDs are evidence targets rather than a hardcoded migration strategy.
