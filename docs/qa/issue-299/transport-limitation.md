# Same-task double Back: browser abort and safe unknown-outcome recovery

Related: #299, #251, #267, #420. This supersedes the initial proposed P3 defect draft, which was not published. Contract review found no demonstrated application defect; no priority or new issue is proposed.

On base `940648810402abd58390c28610629d206cfed73b`, Linux headless Chromium153.0.8010.12 / Playwright1.64.1, 390×844 mobile/touch CSS context, H4 issues two `history.back()` calls in one JS task while the proxy holds the real committed create response. Chromium cancels the POST (`net::ERR_ABORTED`). Guard restoration returns the same Books history entry and visible Sheet; the original response cannot complete the UI. This is synthetic history navigation, not a physical/system gesture.

The applicable contract is the #420 amendment in `docs/adr/0040-specialized-client-operation-lifecycles.md`: unknown-outcome retries retain the original key and submitted facts; fields stay locked until confirmed or definitively refused. Keys/progress do not gain reload persistence. `packages/web/src/books/create.tsx` keeps `createOperation.current` for non-4xx failures and sends its stored input/key on retry. A browser abort is not a definitive refusal. The pending-operation contract promises client exit protection and scoped continuations, not guaranteed survival of the browser's transport.

Saved H4 evidence confirms this contract: Gross45.67 remains visible in the retained form, unknown-outcome status explains recovery, Gross is asserted disabled before retry, and no automatic replay occurs. If the second Back opens a discard question after the failure, Keep editing preserves recovery. Explicit retry uses operation key `d90e44bf-a989-42b8-bdd2-c67c0896a4ab`. Both real201 responses are byte-identical and refer to Expense14. Exactly ONE new Expense and ONE operation row exist in that case, with submitted software/EUR/Gross4567/VAT0/date2026-09-10/supplier-null facts. The final URL is `/books/expenses/14`; all other snapshotted accounting tables and existing rows are unchanged. No duplicate or ledger effect was observed.

User impact shown: one explicit retry is required after the browser cancellation. No lost submitted facts, unsafe retry or incorrect persisted result is demonstrated. The initial FAIL incorrectly required the original transport to complete despite cancellation. H4 is therefore PASS for application unknown-outcome recovery; original transport survival is recorded as a browser limitation. Physical gestures/native Back/OS keyboard remain unverified, and no broader guarantee is inferred.

Only saved evidence and source/ADR contract were rechecked; no browser, full suite, backend or shared component edits were needed. `results.json` retains the old classification in `classificationReview`, while `audit.cjs` explicitly checks stable key, identical responses, persisted facts and exactly one Expense. No transport framework or keepalive change is proposed.
